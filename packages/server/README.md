# @seply/server

**Lane:** B: Server & infra

## Contract

The Hono app factory: Better Auth, /api (push/pull, per-reader state, Proposals, search, export/import, keys, uploads), /mcp, and the Relay, JobRunner and Mailer interfaces. Runtime-agnostic (Workers and Node). Spec: docs/spec/v1/02-architecture.md, 06-mcp.md.

Today (WP-1.1, WP-1.2, WP-1.4, WP-2.5, WP-2.6, WP-3.1, WP-3.2, WP-3.3):

| Export | What it is |
|---|---|
| `createApp({ connect })` | The Hono app. Runtimes mount it at `/api` and pass `connect(env)`, which returns a `DbConnection` (or `null` when there is no database). The app connects at most once per request, lazily, and closes after the response (`waitUntil` on Workers). Nothing is held across requests. |
| `connectPg(connectionString)` | One `pg` client wrapped in Drizzle over the domain schema. The Worker passes `env.HYPERDRIVE.connectionString`. |
| `createAuth(config, db)` | Better Auth, built per request with the Drizzle adapter over the `users`/`sessions`/`accounts`/`verifications` tables from `@seply/domain`. Google when its credentials are set; the OAuth proxy plugin when `AUTH_PROXY_URL` is set; email + password only for tests (below). |
| `readConfig(env)`, `ServerEnv` | The env vars below, validated. Missing `BETTER_AUTH_URL`/`BETTER_AUTH_SECRET` gives a 503 on routes that need auth. |
| `requireUser()` | Middleware: 401 without a session; sets `c.var.user`. |
| `createApp({ relay })` | Optional `Relay`, told about newly logged ops after each commit. Default `noopRelay`. The Worker passes its room relay (WP-3.2); Node rooms come with WP-4.1. |
| `Relay` | `published(exp, batch)`; optional `reader(userId, marks)`, `build(exp, BuildEvent)` (a job's progress) and `handleUpgrade(req, RoomJoin)` (a WebSocket into the Expedition's room; the app has checked access and passes `{ expeditionId, userId, headSeq }`). `publishCommitted` and `publishBuild` call them and only log failures. The room protocol (`hello`, `build`, `poke`) is `@seply/domain`'s `RoomMessage`. |
| `createApp({ jobs })`, `JobRunner` | Optional runner for the job routes (without one they answer 501): `start(db, { expeditionId, kind, input, startedBy })`, `cancel(db, id)`, `retry(db, id)` (a failed or cancelled job's next attempt, from its first step), `wake(db)` (nudges running jobs the runtime lost), and its `registry`. `createJobRunner({ engine, registry, relay })` builds one over a `JobEngine` (`launch(payload)`, `terminate(id)`, `wake?(id)`; one engine instance per attempt, id `<jobId>-<attempt>`) and keeps the `jobs` rows; it announces `queued` and `cancelled` to the room. `JobError` is a refused call (404/409). |
| `JobDefinition`, `JobContext`, `runJob` | A job kind: `{ kind, input (Zod), testOnly?, notification?(job, outcome), run(ctx) }`. `ctx.step(name, fn, { retries, retryDelayMs, timeoutMs }?)` is a durable, retried step whose JSON result is recorded: after a restart the attempt replays `run` from the top and skips steps that returned (so code between steps must be deterministic, and names unique). `ctx.commit(name, produce)` is a checkpoint that commits: `produce` returns `{ ops: OpBody[], label }` in one step (so the op ids are recorded), and the next step appends them as one Change (origin `build`, author: whoever started the job) with `appendOps`, which skips ops already logged; so a retry or restart never logs a commit twice. `ctx.progress(evt)` sends a `BuildEvent` (best effort; job-level events also save the job's `step`/`progress`). `ctx.withDb(fn)` gives one connection. `runJob(payload, steps, deps, registry)` is what an engine calls: it marks the job running, runs the definition, records `complete` or `failed` (with `failureReason(err)`: the message, trimmed), sends the final event and, once, the web push. `JOB_KINDS` is the registry every runtime uses; the build (WP-3.5b) and the writers (WP-3.6) add theirs there. |
| `fakeJob` (`kind: "fake"`, test only) | A fake build: queues N Outline Views (`Test View n`) in one Change, then builds each in its own step and commits it as its own Change, with `building`/`ready` events and two preview Concepts. Input: `views` (1–5), `stepMs` (per build step), `failOnce` (View numbers whose step throws on its first try), `failView: { n, jobAttempts? }` (that View fails on every try while the job's attempt ≤ `jobAttempts`; the View is marked `failed` with the reason, the job fails, and a Retry resumes: Views already ready are kept). Startable only with test credentials on. |
| `createInlineEngine({ deps, registry })` | An in-process `JobEngine` with Workflows' step semantics, for tests: `crash()` drops every running attempt at its next step boundary (a restart; the step in flight is not recorded), `wake(id)` replays it, `settled(id)`, `status(id)`, `recorded(id)`. |
| Web push: `sendPush`, `encryptPayload`, `vapidAuthorization`, `notifyUser`, `readVapid` | Delivery with WebCrypto only (Workers and Node): RFC 8291 `aes128gcm` encryption and an RFC 8292 VAPID JWT. `notifyUser(db, userId, note, { vapid })` sends a `JobNotification` (`{ title, body, url, tag }`) to each of the user's subscriptions and deletes those the push service reports gone (404/410). Off (a no-op) without the VAPID keys. |
| `appendOps(tx, { expeditionId, userId, ops, changes? })` | The one write path for shared content. Inside the caller's transaction: locks the Expedition row, checks the role (owners and editors), skips ops already logged (idempotent by `opId`), applies the rest with `@seply/domain`'s `apply`, assigns gap-free `server_seq`, appends them to `ops`, creates or extends their Changes (one author each), and writes the changed rows. Throws `PushError` on refusal, so the transaction rolls back. |
| `readOps(db, expeditionId, since, limit?)` | Logged ops after `since`, oldest first; each op's `actor` is its Change's author. |
| `createExpedition(tx, { id, userId, ops, change })` | Inside a transaction: a private Expedition row, its owner Collaborator, and its first Change through `appendOps`. Create and import both use it. |
| `readReaderState(db, userId, expeditionId)`, `saveReaderMarks(db, userId, batch)`, `recentPositions(db, userId, limit)` | Per-reader state (WP-2.5): the `reading_status`, `personal_view_settings` and `reader_position` rows of one user, outside the op log. Saving upserts each mark only over an older row (the newest `at` wins; a mark from the future is clamped to now); marks of Expeditions the user can't view are skipped, and personal settings must parse with their View Type's personal schema (else skipped). |
| `Relay.reader?(userId, marks)` | The reader channel: told after a save, with that user's accepted marks only (never anyone else's). Optional; the live relay (M4) will forward it to the reader's other devices. |
| `search(db, { userId, q, includePublic?, limit? })` | Global search (spec §2.8), grouped `{ expeditions, concepts, tags }`. `parseQuery(q)` splits free text from `#tag` filters; `buildSearchQueries(params)` returns the three SQL queries (or null for an empty query); `searchableExpeditions(userId, includePublic)` is the access rule they all share: Expeditions the user collaborates on (any role), plus public ones when `includePublic`; never unlisted ones they don't collaborate on, never Trash. |
| `createApp({ blobs })`, `BlobStore` | Optional `blobs(env)`: where Source files and segments go (`put`, `get`, `delete`). `r2BlobStore(bucket)` wraps an R2 binding (the Worker's `SOURCES`); `memoryBlobStore()` is for tests. Without one, the Source routes answer 503. Keys: `sourceBlobKeys(expeditionId, sourceId)` → `sources/<exp>/<source>/raw` and `…/segments.json`. |
| `parseFile({ bytes, filename, type })`, `parsePaste(text, title?)`, `parsePrompt(text, title?)` → `ParsedSource` | Reading a Source (§5.2 step 1, no LLM; `src/sources/`): `{ kind, title, mime, segments: SegmentsDoc }`. The format comes from the bytes first (`%PDF-`, zip), then the extension and type: **chat exports** (`chat-exports.ts`: ChatGPT `conversations.json`, the branch ending at `current_node`, user and assistant text only; Claude `conversations.json`, `chat_messages` text blocks; Gemini's Takeout “Gemini Apps” My Activity JSON, oldest first, responses from HTML; a ChatGPT or Claude export's zip), **PDF** (`pdf.ts`, unpdf, one segment per page; no OCR), **DOCX** (`docx.ts`: `word/document.xml` paragraphs, Heading1–4 and Title as headings, list paragraphs as items), **HTML** (`html.ts`, node-html-parser to markdown; scripts and styles dropped), **Markdown** and **TXT**. Text formats and pastes get speaker detection (`@seply/domain`'s `segmentText`), so a chat saved or pasted as text becomes turns. Throws `SourceError` (400 unreadable or empty, 413 over 25 MB, 415 unsupported). |
| `addSource(db, blobs, { expeditionId, userId, parsed, raw })`, `readSegments(db, blobs, expeditionId, sourceId)` | Adding: checks the role (owners and editors; 404/403 as `PushError` before anything is stored), puts the raw file and the segments blob, then logs `source.add` as one Change, “Added the Source “…””, through `appendOps` (the blobs are deleted again if that fails). Reading (the `SourceReader` port's read): `{ source, segments }` or null (no such Source, no segments stored, e.g. imported from JSON). Only keys under the Expedition's own prefix are ever read, since `source.add` rows come from the op log, which clients write. No access check: callers check. |
| `loadState(db, id)`, `writeState(db, before, after)` | The tables as a projection of the log: read one Expedition into a `DomainState`; write the rows that differ between two states. |

**Routes** (under `/api`):

- `GET /health`: `{ ok, db, branch }`. `db` is `select current_database()`, `"unconfigured"` with no database, `"error"` (503) when it fails.
- `/auth/*`: Better Auth (sign-in, callbacks including `/auth/callback/google/oauth-proxy`, session, sign-out).
- `GET /me`: `{ user: { id, email, name } }`, or 401.
- `POST /expeditions` `{ title? }`: creates a private draft Expedition; the creator becomes its owner Collaborator, and a non-empty title is logged as an `expedition.set` op in a first Change, "Created the Expedition" (one transaction). 201 with an `ExpeditionSummary` (`id`, `title`, `summary`, `visibility`, `status`, `role`).
- `GET /expeditions`: `{ expeditions: LibraryCard[] }`, every Expedition I collaborate on, not in Trash, newest first. A `LibraryCard` (WP-2.7, the Library's cards) is an `ExpeditionSummary` plus `tags` (Expedition Tags, A–Z), `collaborators` (`{ id, name, image, role }`, owner first; no emails), `counts` (`{ concepts, views }`, live ones), `bestViewType` (the best View's View Type, else the first View's in rail order, null with no Views: the Library draws that View Type's fixed thumbnail) and `updatedAt` (ISO: the latest Change, else the id's creation time). `libraryCards(db, summaries)` adds them in five queries.
- `POST /import` (signed in), body: an Expedition in our JSON (any version, at most 25 MB): validated and upgraded, every entity id re-minted (`@seply/domain`'s `importExpeditionJson`), then created as a new private Expedition owned by the importer, with its ops logged as one "Imported from file" Change (origin `import`) through `appendOps`, all in one transaction. 201 `{ expedition: ExpeditionSummary, counts: { concepts, relationships, views } }`; 400 `{ error, message, issues }` for an invalid file (nothing written), 413 too large. `importExpedition(db, { userId, file })` is the same without HTTP.
- `POST /push` `{ expeditionId, ops: Op[], changes?: [{ id, label?, origin? }] }` (signed in): validates every op with the domain schemas (its `expeditionId` and `actor` must match the request and the signed-in user, `schemaV` the current one, no duplicate ids), then `appendOps` in one transaction, then `Relay.published` with the newly logged ops. 200 `{ headSeq, results: [{ opId, serverSeq }] }`, one result per op in batch order; a retry returns the same results and applies nothing. All or nothing: 400 invalid op, 403 a role that may not make it, 404 an Expedition the caller can't view, 409 an op that doesn't apply or a Change of another author. `origin` is `human` (default), `restore` or `merge`; builds, AI and imports are server-side. At most 1000 ops.
- **Per-reader state** (signed in; private to the reader, spec §1.7):
  - `GET /reader/expeditions/:id`: `{ reading: ReadingMark[], viewSettings: ViewSettingsMark[], position: PositionMark | null }`, my state in one Expedition I can view (404 otherwise).
  - `POST /reader` (a `ReaderBatch`: `{ reading?, viewSettings?, positions? }`, marks across Expeditions): saves them, newest winning per row. 200 `{ saved: { reading, viewSettings, positions }, skipped: [expeditionId] }`; 400 for a malformed batch. One route serves a single mark, a browser's offline queue and an anonymous reader's marks merged on sign-in.
  - `GET /reader/recent?limit=3` (max 20): Continue reading, `{ items: [{ expedition: { id, title, summary, visibility, status }, position }] }`, my most recent positions in Expeditions I can still view, newest first.
- `GET /search?q=<text and #tags>&public=0|1&limit=<n>` (signed in): `{ expeditions, concepts, tags }`. Free text runs `websearch_to_tsquery('english', …)` against the weighted `search` vectors, or matches titles and aliases fuzzily with pg_trgm (`%`, `<%`), ranked by `ts_rank_cd` plus word similarity. Each `#tag` must be on the Concept (Concept Tags) or Expedition (Expedition Tags); Tags are suggested by prefix (the free text, else the last `#tag`) with their counts. Expeditions: at most 10; Concepts: `limit` (default 20, max 50), each with its Expedition's title; Tags: at most 8. 400 for an invalid query.
- **Jobs** (signed in; spec §2.5). A job or Expedition the caller can't view is a 404; running, cancelling and retrying need `useAi` (owners, editors), else 403.
  - `POST /expeditions/:id/jobs` `{ kind, input? }`: 201 `{ job }` (a `Job`: `id`, `expeditionId`, `kind`, `input`, `startedBy`, `status` queued|running|complete|failed|cancelled, `step`, `progress` 0–1, `error`, `attempt`, `createdAt`, `updatedAt`). 400 for an unknown kind (test-only kinds count as unknown without test credentials) or invalid input.
  - `GET /expeditions/:id/jobs`: `{ jobs }`, the 20 most recent, newest first. `GET /jobs/:id`: `{ job }`.
  - `POST /jobs/:id/cancel`: `{ job }` cancelled (409 if it had ended). `POST /jobs/:id/retry`: `{ job }` queued as its next attempt (409 unless failed or cancelled).
- `GET /expeditions/:id/live` (signed in, can view): the WebSocket into the Expedition's room, handed to `Relay.handleUpgrade`; 426 without an upgrade, 501 without a live relay. Anonymous readers join with WP-4.1.
- **Web push** (spec §2.5): `GET /web-push/key` → `{ publicKey }` (404 when off). Signed in: `POST /web-push/subscriptions` (a browser's `PushSubscription.toJSON()`; https endpoints only, plus `http://localhost` with test credentials on) → 201, idempotent, one row per endpoint; `DELETE /web-push/subscriptions` `{ endpoint }` removes your own.
- **Sources** (WP-3.1; `src/sources/routes.ts`):
  - `POST /sources/:expeditionId` (signed in; owners and editors): `multipart/form-data` with `file` (and optional `title`), 25 MB cap (413 above it); or JSON `{ type: "paste" | "prompt", text, title? }` (a paste gets speaker detection; a prompt is one segment `s1`). 201 `{ source, segments: { kind, format, count, chars } }`; 400/415 `{ error: "unreadable", message }` when it can't be read (nothing stored); 404 an Expedition the caller can't view; 403 a viewer; 503 without a blob store.
  - `GET /sources/:expeditionId/:sourceId` (anyone who can view, like `/pull`): `{ source, segments: SegmentsDoc }` (blob keys stay on the server); 404 when the Source or its text isn't there.
  - `GET /sources/:expeditionId/:sourceId/file` (anyone who can view): the raw file, always as an attachment (`content-disposition`, `nosniff`, `sandbox` CSP).
- `GET /pull?expedition=<id>&since=<serverSeq>&limit=<n>`: `{ headSeq, ops: LoggedOp[], more }`, the ops after `since` (default 0), at most `limit` (default and max 1000). For anyone who can view the Expedition, signed in or not where Visibility allows; 404 otherwise.
- **AI** (WP-3.3, signed in; spec §5.6, §3.10). No response ever carries a key, whole or encrypted (`ai.test.ts` calls every GET route with a key stored and checks):
  - `GET /ai`: `AiOverview`: `mode` (`instance` | `byok`), `ready`, `active` (the provider builds use now, its label and models per stage; null when not ready), `keys` (BYOK: `{ provider, last4, createdAt }` per stored key), `providers` (BYOK: the four providers with their default models), `settings` (`provider`, `models`, `askCapUsd`) and `defaultAskCapUsd`.
  - `PUT /ai/keys/:provider` `{ apiKey }` (BYOK only, else 409): stores or replaces my key for `anthropic`, `openai`, `google` or `gateway`, AES-GCM encrypted. 200 `{ key: { provider, last4, createdAt } }`; 400 for something that isn't key-shaped (the message never echoes it); 404 unknown provider; 503 without `AI_KEYS_MASTER_KEY`.
  - `POST /ai/keys/:provider/test` (BYOK only): decrypts my key on the server and checks it with the provider without spending (`@seply/ai`'s `testKey`): `{ ok: true }` or `{ ok: false, reason: "rejected" | "unreachable" | "error" }`. 404 without a key.
  - `DELETE /ai/keys/:provider`: 204, or 404 when there was none.
  - `PATCH /ai/settings` `{ provider?, models?, askCapUsd? }`: which of my keys builds use (null: the first I have, in `BYOK_PROVIDERS` order), model overrides per provider and stage (BYOK; instance mode uses the operator's `AI_MODEL_*`), and the per-ask cap (up to `MAX_ASK_CAP_USD`, $50; null resets to $0.50). Returns the `AiOverview`.
  - `POST /ai/estimate` `{ sourceChars, views? }`: `{ estimate: BuildEstimate }` on the provider and models builds would use (no key is decrypted); 409 `{ error: "no-key" | "not-configured" }`.

**Env** (`ServerEnv`): `BETTER_AUTH_URL` (this deploy's origin), `BETTER_AUTH_SECRET` (the same on every deploy), `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `AUTH_PROXY_URL` (production's origin, on previews and production), `AUTH_TRUSTED_ORIGINS` (comma-separated, `*` allowed), `AUTH_TEST_CREDENTIALS`, `DB_BRANCH`, and for web push `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` (base64url) and `VAPID_SUBJECT`. See [docs/ops/deploy.md](../../docs/ops/deploy.md#sign-in-better-auth).

**AI** (WP-3.3; `ai.ts`, `ai-config.ts`, `ai-keys.ts`):

| Export | What it is |
|---|---|
| `resolveAi(db, env, userId, options?)` | Whose key and which models a request or job uses: `{ ok: true, setup: AiSetup, askCapUsd }` or `{ ok: false, reason: "no-key" \| "not-configured" }`. Instance mode: the operator's key and `AI_MODEL_*` over the provider's defaults. BYOK: my preferred provider (else the first I have a key for), my key decrypted for this call only, my overrides. Pass `setup` to `@seply/ai`'s `modelFor(setup, stage, meter)`. The setup holds the key in the clear: never persist or return it. |
| `readAiConfig(env)` | `{ mode, instance, instanceModels, masterKey }`. The instance key, first found: `AI_GATEWAY_API_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GOOGLE_GENERATIVE_AI_API_KEY`, then `OPENAI_COMPATIBLE_BASE_URL` (+ `OPENAI_COMPATIBLE_API_KEY`, default `none`). An unknown `AI_KEY_MODE` is a `ConfigError` (503). |
| `readAiSettings(db, userId)` | My `ai_settings` row: `provider`, `models` (per provider and stage), `askCapUsd` (default $0.50). |
| `importMasterKey`, `sealKey`, `openKey` | AES-GCM with Web Crypto (Workers and Node): a fresh 12-byte IV per key, and the user id and provider as additional data, so a ciphertext moved to another row doesn't decrypt. The master key must be 32 bytes, base64. |
| `saveKey`, `listKeys`, `deleteKey`, `loadKey` | The `ai_keys` rows (one per user and provider). `listKeys` returns `{ provider, last4, createdAt }` only; `loadKey` decrypts, for the server's own use. |

**AI env:** `AI_KEY_MODE` (`instance`, the default, or `byok`), `AI_GATEWAY_API_KEY` (the hosted instance key), the self-host alternatives above, `AI_MODEL_SKIM`, `AI_MODEL_CURATOR`, `AI_MODEL_WRITER` (instance mode), and `AI_KEYS_MASTER_KEY` (BYOK: 32 random bytes, base64, `openssl rand -base64 32`; changing it makes stored keys unreadable). Deploys: [docs/ops/deploy.md](../../docs/ops/deploy.md).

**Test credentials:** email + password sign-in is on only when `AUTH_TEST_CREDENTIALS=1` **and** `BETTER_AUTH_URL` is a localhost URL, so a deployed Worker can never enable it.

**Migrations:** `drizzle.config.ts` generates SQL migrations from `@seply/domain`'s schema into `drizzle/` (committed). `db:generate` after a schema change; `0002_ai_settings.sql` adds `ai_settings` (WP-3.3). `0001_search.sql` is hand-written (`drizzle-kit generate --custom`): it adds `pg_trgm`, the trigger-maintained `search` tsvector columns on `expeditions` (title A, summary B) and `concepts` (title and aliases A, summary B, overview C, live article sections D; an article section's insert, edit or delete re-indexes its Concept), `concepts.search_title` (title + aliases), GIN indexes on the vectors, pg_trgm GIN indexes on `expeditions.title` and `concepts.search_title`, and `lower(tag)` indexes on both tag tables. These columns are not in the Drizzle schema: only search reads them, through SQL; `db:migrate` (`scripts/migrate.mjs`) applies them to `$DATABASE_URL` and is what CI runs before each deploy.

**Tests** run the app over in-memory PGlite (with its `pg_trgm` contrib extension loaded) with the committed migrations applied (`src/test-harness.ts`): search (query parsing, parameter binding, the trigger-maintained vectors, full-text, fuzzy and `#tag` matching, and access: a private Expedition never appears for a stranger, unlisted never appears in global search, public only with the toggle), the push/pull apply path (ordering, idempotency, roles, validation, transactionality, and the compute sample round-tripped through the log), import of both fixtures (counts, one Change, owner, fresh ids, rejections), per-reader state (`reader.test.ts`: newest wins, privacy between readers, personal settings validated, future marks clamped, Continue reading order, the reader channel), the OAuth proxy round trip between a preview and production app with Google's token endpoint stubbed, AI (`ai.test.ts`: AES-GCM round trip, fresh IVs, failure under another master key or row; no route returns a stored key, its ciphertext or IV; BYOK add, replace, test, prefer, override, delete and isolation between readers; instance mode; settings bounds), jobs on the inline engine (`jobs/jobs.test.ts`: one Change per commit, a forced step failure retried, a simulated restart resumed with nothing logged twice, failure reasons, cancel, retry resuming past built Views, the room events and the notification, route permissions), and web push (`push/webpush.test.ts`: the RFC 8291 test vector, decryption as a browser does it, the VAPID signature, gone subscriptions, the routes). Sources: `src/sources/parse.test.ts` reads one fixture per format, and the research doc; `src/sources/routes.test.ts` covers upload, paste and prompt, the logged Change and the blobs, the 25 MB cap, roles, Visibility, and a pushed `source.add` naming another Expedition's blobs (never read).

**Source fixtures** (`fixtures/sources/`): synthetic, written for WP-3.1 on public topics (tides, photosynthesis, primes, volcanoes, bees, printing): exports in ChatGPT's, Claude's and Gemini's shapes, a pasted chat, Markdown, TXT and HTML. `scripts/build-source-fixtures.mjs` builds `sample.pdf`, `sample.docx` and `chatgpt-export.zip` from text in the script (`node scripts/build-source-fixtures.mjs`; reproducible). Never real chats or files.
