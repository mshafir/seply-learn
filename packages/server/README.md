# @seply/server

**Lane:** B: Server & infra

## Contract

The Hono app factory: Better Auth, /api (push/pull, per-reader state, Proposals, search, export/import, keys, uploads), /mcp, and the Relay, JobRunner and Mailer interfaces. Runtime-agnostic (Workers and Node). Spec: docs/spec/v1/02-architecture.md, 06-mcp.md.

| `JobDefinition`, `JobContext`, `runJob`                                                                                 | A job kind: `{ kind, input (Zod), testOnly?, notification?(job, outcome), run(ctx) }`. `ctx.step(name, fn, { retries, retryDelayMs, timeoutMs }?)` is a durable, retried step whose JSON result is recorded: after a restart the attempt replays `run` from the top and skips steps that returned (so code between steps must be deterministic, and names unique). `ctx.commit(name, produce)` is a checkpoint that commits: `produce` returns `{ ops: OpBody[], label }` in one step (so the op ids are recorded), and the next step appends them as one Change (origin `build`, author: whoever started the job) with `appendOps`, which skips ops already logged; so a retry or restart never logs a commit twice. `ctx.progress(evt)` sends a `BuildEvent` (best effort; job-level events also save the job's `step`/`progress`). `ctx.withDb(fn)` gives one connection. `ctx.announceProposals()` pokes the room after a job writes Proposals (best effort). `runJob(payload, steps, deps, registry)` is what an engine calls: it marks the job running, runs the definition, records `complete` or `failed` (or `paused`: a step threw @seply/ai's `SpendingCapReached`, which is never retried; `ctx.step` then throws `JobPaused`, which a definition must let propagate; `isJobPaused(err)`) (with `failureReason(err)`: the message, trimmed), sends the final event and, once, the web push. `JOB_KINDS` is the registry every runtime uses: `build`, `article`, `grow` and the test-only `fake`. `JobDeps.services` (`JobServices`: `env` for `resolveAi`, `blobs` for Source segments, `views`, the `ViewReader` (`@seply/views/inspect`'s `readView`, which only apps may import), and, for tests, `model`, `curator` sizes and `writers` batch sizes) reaches a job as `ctx.services`. | `buildJob` (`kind: "build"`, WP-3.5b; `jobs/build.ts`)                                                                  | The build (spec §5.2 step 3): the curator agent turns the Expedition's Sources into its Concept set and chosen Views; the stages are `@seply/ai`'s. Input (`BuildJobInput`): `viewIds?` (Views already queued, as the create flow saves them, built into their own rows, best first; what `POST /expeditions/:id/build` passes), `goals?` (the understanding note weighs them), `views` (chosen Views to queue, best first, each a `BuildViewChoice`: `{ viewType, label, question?, why? }`, at most 8), `sources?` (Source ids; all by default), `capUsd?` (the spending cap; 2× `estimateFor` by default). Steps: `plan` (the Sources' segments, the AI setup, whole or chunks, which Views: Views already `ready` are skipped, other Views queued in the Expedition are built too), the Change "Queued N Views" (each `queued` with placeholder settings; a draft Expedition goes `building`), `note` (the understanding note, kept in the step), `concepts` (or `concepts: chunk i of n`, then `concepts: merge`) committed as one Change "Found N Concepts in M Sources" (skipped when the Expedition already has Concepts, as on a Retry), then per View `View n: build` and its own Change "Built <label>" (the first ready View becomes the best View and the Expedition `ready`), or "Could not build <label>" (`failed`, with `failReason`) and on to the next View. `build` events: `Finding Concepts · N so far` as the set grows, each View `building` with `previewNodes`, then `ready`, or `failed` with its `reason`. AI steps retry twice (spec §5.6); a step that still throws fails its View with `failureReason`. The job ends `failed` when any View failed ("1 of 3 Views couldn't be built: …"), and a Retry rebuilds only those. The spending cap (`capUsd`, raised once per Continue: `ctx.job.capRaises`) pauses it: a stage that reaches it throws `SpendingCapReached` out of its step, and the attempt ends `paused` (`JobPaused`; never swallowed by the per-View handling). Continue (`POST /jobs/:id/continue`) and Retry both plan again from the log: the Concept set and `ready` Views are kept, `queued` and `failed` ones are built. The AI setup is resolved again in every step, never stored. Needs `services.env`, `services.blobs` and `services.views`. **The writers (WP-3.6)** run last, after every View (even when one failed): `runWriters` (`jobs/writers.ts`) plans in a step (`write: plan`, @seply/ai's `planWriters`: every Concept without an overview, core first, in batches of 10; then every core Concept without an article, in batches of 3), then runs `write n` steps up to `WRITER_PARALLEL` (3) side by side, each from the same meter (combined after with `combineSpend`), and commits each batch as its own Change ("Wrote overviews for Alder C5, Hub motor and 8 more", "Wrote the article for Alder C5") in plan order once its wave is back; a Concept deleted meanwhile is skipped. Each step checks that every provenance ref resolves (`unresolvedProv`) before it returns. Events: job-level `Writing overviews · 20 of 47`, then `Writing articles · 3 of 7`. A cap reached in a wave pauses the job after that wave's other batches are committed. A batch that still fails after its retries, or Concepts the model left out twice, are skipped, and the job ends `failed` ("Couldn't write 3 overviews. Retry to write them."); Retry plans again from the log, so only what is missing is written. The Views take the progress bar from 0.3 to 0.8, the writers the rest. |

  - `GET /.well-known/oauth-protected-resource[/mcp]` (RFC 9728) and `GET /.well-known/oauth-authorization-server[/api/auth]` (RFC 8414), served by Better Auth's handler.
  - Without a valid Bearer token, `/mcp` answers 401 with `WWW-Authenticate: Bearer resource_metadata="<origin>/.well-known/oauth-protected-resource/mcp", scope="…"`.
- **Auth** (`auth.ts`): Better Auth is the OAuth 2.1 server: `jwt()` (signing keys in `jwks`; no JWT header on session reads), `mcp({ resource: <origin>/mcp, loginPage: "/sign-in", consentPage: "/consent", scopes })` (`@better-auth/mcp`, on `@better-auth/oauth-provider`'s tables), `cimd()` when the runtime passes `cimdFetch` (Client ID Metadata Documents; dynamic client registration stays off), and `apiKey()` (`@better-auth/api-key`, prefix `sl_`, metadata on, no rate limit). `mcp/agent.ts` `resolveAgent` takes the Bearer token: `sl_…` is checked with `verifyApiKey`; anything else must be a JWT signed by our `jwks` (read from the database, never fetched over HTTP), issuer `<origin>/api/auth`, audience `<origin>/mcp`. The **Agent** is `{ userId, label, scopes, expeditions }`: the token's scopes (`permissions.mcp`) or the OAuth grant's (`scope` claim), and its Expedition restriction (the token's `metadata.expeditions`, or `agent_grants` for the user and client). `agentCaller(agent, exp)` is the `Caller` for `expeditionAccess`: `agent.allowed` is false outside the restriction, so the Expedition reads as not found.
- **Tools** (`mcp/tools.ts`): names, descriptions and inputs are `@seply/ai`'s `MCP_TOOLS` (built from the curator tools). `runTool` checks the tool's scope, then the handler checks the Collaborator role through `expeditionAccess` (and `canPropose` for `propose_changes`), and answers in markdown (`mcp/render.ts`); a refusal comes back as a tool error (`isError`) the agent reads. Each call on an Expedition renews `Relay.agentPresence` (5 minutes, labelled "<token or client name> (via MCP)").
  - `create_expedition` stores the Sources' segments in the blob store, runs `stageFirstBuild`, and logs one Change (origin `mcp`, "Built from 2 Sources by Claude Code (via MCP)") through `createExpedition`: private, owned by the user. Needs `views` (a ViewReader) and blobs.
  - `propose_changes` runs `stageProposal` and writes one Proposal (origin `mcp`, author the user) with `createProposal` / `addProposalItems`, then `announceProposals`. Views can be proposed only with `views`.
  - `list_my_proposals` and `withdraw_proposal` use `listAuthoredProposals` and `withdrawProposal` (`proposals.ts`): withdrawing dismisses the pending items (by the author) and marks the Proposal `withdrawn`.
- **Connected agents** (`agents.ts`, under `/api/agents`, signed in): `GET /agents` → `{ tokens, grants, scopes }`; `POST /agents/tokens` `{ name, scopes, expeditions?: id[] | null, expiresInDays? }` → 201 `{ token, key }` (the key only here; Expeditions must be ones the user collaborates on, else 404); `DELETE /agents/tokens/:id`; `POST /agents/consent` `{ clientId, expeditions }` (the consent screen, before Better Auth's `/oauth2/consent`) → 204; `DELETE /agents/grants/:clientId` (forgets the consent, deletes its access and refresh tokens and its restriction).
- **Options:** `AppOptions.views` (`@seply/views/inspect`'s `readView`) and `AppOptions.cimdFetch` (a metadata fetch the runtime can make safe: the Worker's refuses redirects, and Workers can't reach private addresses; Node will use `@better-auth/cimd/node`).
- **Schema** (`0007_mcp.sql`): `api_keys` is now the API key plugin's table (the old one was never written), plus Better Auth's `jwks`, `oauth_clients`, `oauth_resources`, `oauth_client_resources`, `oauth_access_tokens`, `oauth_refresh_tokens`, `oauth_consents`, `oauth_client_assertions`, and our `agent_grants` (`user_id`, `client_id`, `expedition_ids`).
- **Keep `BETTER_AUTH_SECRET` stable:** the JWT signing keys in `jwks` are encrypted with it. After a rotation, delete the `jwks` rows (a new key is made on the next token; connected agents sign in again).
