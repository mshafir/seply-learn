# @seply/ai

**Lane:** E: AI

## Contract

The curator agent (AI SDK 7 ToolLoopAgent), its tools and view.inspect checks, the skim, writers, the playbook, BYOK/instance providers and cost accounting. Spec: docs/spec/v1/05-ai.md.

Today (WP-3.3, providers, keys and cost; `ai` 7.x with `@ai-sdk/anthropic`, `openai`, `google`, `openai-compatible`, and the gateway provider from `ai`):

### How the next stages use it

```ts
// In a request or job (server side):
const ai = await resolveAi(db, env, userId)        // @seply/server
if (!ai.ok) return fail(ai.reason)                 // "no-key" | "not-configured"
const estimate = estimateFor(ai.setup, sourceChars) // shown before Create
const meter = new SpendMeter({ kind: "build", capUsd: estimate.capUsd })
// (an ask: new SpendMeter({ kind: "ask", capUsd: ai.askCapUsd }))
const agent = new ToolLoopAgent({ model: modelFor(ai.setup, "curator", meter), … })
// SpendingCapReached → pause the job (Continue: meter.raise(); Stop), or end the ask.
// Checkpoint meter.toJSON() with the job; resume with SpendMeter.from(state).
```

The setup holds the key in the clear: keep it inside the request or job, never in a job's persisted state (persist the user id and re-resolve).

### The estimate's accuracy

`src/estimate.test.ts` checks the estimate against real calls on the committed fixtures (the research doc, and the compute sample's prose standing in for its chat; `src/fixture-sources.ts`), recorded in `src/estimate-actuals.json` by `scripts/measure-estimate.ts` through the AI Gateway (it spends real money, well under $1, so it isn't part of `pnpm test`: `node --env-file=../../apps/worker/.dev.vars --experimental-transform-types scripts/measure-estimate.ts`). Each call is the curator's first step (the whole Source in context, cached, and the understanding note written back) on the cheap model of each tokenizer family and on Claude's tiers. Token estimates are within 10% and cost estimates within 9% of what the gateway billed (the bar is 30%), and the price table reproduces the gateway's billed cost within 2%. Re-run it when a model, price or tokenizer changes.

The build estimate's step shapes (tool steps per Concept and View, output per step, the writers' batches) are design figures from spec §5.2 and the seeding prototype, not yet measured: no build runs until WP-3.5b. Re-fit `STEP` against real builds then.

### Curator tools and checks (spec §5.3)

| Module    | Exports                                                                                                                                                                                                              |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tools`   | `createCuratorTools(opts)` → `{ tools, stage, inspect, commit }`. `TOOL_NAMES` (the model-facing name → the spec's name). Types `CuratorTool`, `ToolResult`, `CuratorCommit`, `CommitResult`, `CuratorToolsOptions`. |
| `stage`   | `StagingArea`: the staged op bodies over a working copy of `DomainState` (`state`, `base`, `staged`, `stage(bodies)` all-or-nothing, `take()`, `discard()`).                                                         |
| `inspect` | `inspectView(state, viewId, { views, sources })` → `ViewInspection` (`reading`, `layout?`, `problems`, `warnings`, `ok`).                                                                                            |
| `checks`  | `checkView(state, viewId, { sources })`, `checkExpedition(state)` → `Finding[]` (`severity` problem/warning, `code`, `message`, `concepts?`); `MIN_FILL`, `MIN_ROWS`.                                                |
| `search`  | `searchExisting(state, query, limit?)`, `normalizeTitle`.                                                                                                                                                            |
| `ports`   | `ViewReader`, `ViewReading`, `LayoutReport`; `SourceReader`, `Segment`, `memorySourceReader(sources)`.                                                                                                               |

- **Tools** (model-facing names; providers allow no dots): `concept_create`, `concept_update`, `relationship_add`, `relationship_remove`, `attribute_define`, `view_build`, `view_inspect`, `source_read`, `search_existing`, and `view_commit` when `onCommit` is given. Each is `{ description, inputSchema, execute }`, the shape AI SDK's `tool()` takes. Inputs are Zod schemas over the `@seply/domain` op schemas (`view_build` is a union with one variant per View Type, carrying that type's settings schema), and `execute` parses its input again whoever calls it. Writing tools return `{ ok: true, id | viewId }` or `{ ok: false, error }`; nothing throws for a bad call.
- **Staged ops:** every write becomes op bodies, validated (`parseOpBody`) and applied (`apply`) to the working copy at once, so the domain's refusal comes back as the tool's error and nothing of that call is staged. Ids are minted with `opts.newId` (ULIDs by default). New Views start `building`, last in the rail.
- **`view_inspect`:** the `ViewReader`'s reading of the View (text) and layout metrics, plus the checks. A `cluttered` layout is a problem.
- **Checks** (ported from `prototypes/seeding/validate.py`, and the build-view playbook's rules). Problems: a Relationship with a missing end; settings naming Concepts, Kinds, Relationship Types or Attributes that don't exist (`dangling-ref`); more than one `part-of` parent in a View that reads part-of (Outline, Anatomy, Learning path) unless its `placement` settles it; Comparison Table: fewer than 3 rows, a criterion column without a priority, a class statement ("Enclosed printers meets Runs ABS") not applied to a member row, a column under 70% filled (a sparse must-have only warns), `chosen` without a citation of the reader deciding (a `user` chat turn or a prompt Source, on the row or a linked `decision` Concept); Cause & Effect: no outcome, nothing into the outcome, lever→lever links, a lever's `part-of` steps not in `fold`. Warnings: Concepts with no Relationships; an outcome that cites no reader turn.
- **`commit({ label, views? })`:** takes everything staged as one Change. It inspects every View the staged ops create or change, plus `views`, and checks the Expedition; with any problem it returns `{ ok: false, blocked }` and keeps the staged ops. Otherwise it marks those Views `ready`, returns `{ ok: true, label, bodies, views }`, calls `onCommit`, and makes the state the new base.
- **Ports:** the app that runs the job fills them. `views` is `@seply/views/inspect`'s `readView` (`{ read: readView }`); `sources` is WP-3.1's segment store (`memorySourceReader` meanwhile). This package never imports `@seply/views` (spec §2.1).

### The curator's build stages (spec §5.2, WP-3.5b)

The step functions of the build. Each is a plain async function over a `DomainState` that returns op bodies and never writes; `@seply/server`'s `build` job runs each in its own durable step and commits what it returns.

| Module | Exports |
| --- | --- |
| `curator/playbook` | `playbook(name)`, `viewTypeDoc(viewType)`: the playbook files (`playbook/*.md`: `_contract`, `skim`, `extract`, `merge`, `build-view`, `write`, `grow` (WP-4.4), moved from `prototypes/seeding/prompts/`) and the View Type definitions (`docs/view-types/*.md`). They come from `src/playbook/generated.ts` (`PLAYBOOK_FILES`, `VIEW_TYPE_DOCS`; see "The playbook" below): **after editing a playbook file or a View Type definition, run `pnpm --filter @seply/ai playbook`**. |
| `curator/sources` | `CuratorSource` (`{ id, title, segments }`), `renderSources` (each segment tagged `[t14 · user]`, `[s3 · heading]`), `renderSourceIndex` (ids and first words, for chunk mode), `planSources(sources, { provider, modelId }, { maxTokens?, chunkTokens? })` → `{ mode: "whole" }` when the estimated tokens fit `WHOLE_SOURCE_MAX_TOKENS` (150k), else `{ mode: "chunks", chunks }` of about `CHUNK_TOKENS` (40k) of consecutive segments. |
| `curator/loop` | `runLoop`: one `ToolLoopAgent` run with the prompt cache laid out for a long loop (the instructions, the Sources part of the first message, and a rolling breakpoint on the newest message: three of Anthropic's four), a step budget and a `done()` stop. `rollCache`. |
| `curator/curator` | `understand` (the understanding note: what the reader wanted, decided, left open; kept in the job, never shown). `extractConcepts` (the Concept set over the whole Sources, or one chunk with the earlier chunks' Concepts in its state; the agent is asked to fix any dangling Relationship before it returns). `mergeConceptSet` (chunk mode: `autoMerge` of exact normalized title/alias matches of one Kind, then the agent's merge-and-tidy pass with `duplicateCandidates` and a `concept_merge` tool over the domain's `mergeConcepts`). `buildView` (one queued View: the agent fills what it needs, `view_build` (always this View), `view_inspect`, self-review, then `view_commit({ review })`, refused until the View was built and while `view_inspect` finds problems, or `view_fail({ reason })`; an agent that stops without either is nudged twice, then the View fails with a plain reason) → `{ status: "ready", bodies, label, review, warnings }` or `{ status: "failed", reason }`. Helpers: `placeholderSettings(viewType)` (valid settings for a queued View), `applyBodies`, `describeConcepts` (the Concept set as the agent reads it), `previewNodes(state, staged)` (the Concepts a building View touches, for `build` events), `conceptSetLabel` ("Found 84 Concepts in 3 Sources"), `MAX_STEPS`. |
| `testing` (`@seply/ai/testing`) | `scriptedModel(script)`: a model that answers each call from a script (tool calls or text), so a build runs end to end with no provider; `idsFrom(turn, tool)`; `writerScript({ bad?, skip? })`: a writer answering every overview or article batch with realistic output that cites each Concept's own segments (`bad` adds refs that don't resolve; `skip` leaves Concepts out). Tests only. |

**Real builds** (`apps/server-node/scripts/real-build.ts`; the exports and summaries are in `fixtures/builds/` for owner review): the WP-3.4 e-bike chat (6.4k characters) on Opus 5.5, 4 Views: 47 Concepts, 3 Views ready and passing `view.inspect`, the Timeline failed with a plain reason (the chat has no dates), 12.5 min, $2.99 billed. The research doc (32k characters) on Sonnet 5.5, 4 Views: 69 Concepts, all 4 ready and passing `view.inspect`, 12.5 min, $2.91 billed. Both were interrupted on purpose and resumed with no duplicate Views. The research doc hit its default spending cap ($1.74, 2× the estimate) after two Views, so **the estimate's `STEP` figures are low by about 2–3×**; re-fit them from these summaries.

Every stage takes an `onStep` callback with the working copy (live counters, preview nodes) and a `newId`. The model comes from `modelFor(setup, "curator", meter)`; a `SpendingCapReached` thrown by the metered model propagates out of the stage.

### The writers (spec §5.2 step 4, WP-3.6)

`writers/writers.ts`. Plain async functions over a `DomainState` that return op bodies and never write, like the curator's stages; `@seply/server` runs them in the `build` job (each batch its own durable step and Change) and in the `article` job ("Write the article": one Proposal).

| Export | What it is |
|---|---|
| `planWriters(state, { overviews?, articles? })` → `WriterPlan` | What is still owed, in batches (`WRITER_BATCH`: 10 overviews, 3 articles): every live Concept without an overview (core first, then the most connected), then every core Concept without an article section. Planning again after a commit plans nothing written. |
| `coreConcepts(state)` | The core Concepts: those the curator pinned `weightPin: "core"`; when none are pinned, the most connected 15% (`CORE_FALLBACK`: at least 3, at most 20), never an `aux` one. |
| `writeOverviews(o)`, `writeArticles(o)`, `writeBatch(mode, o)` → `WriteResult` | One call on the writer model (`modelFor(setup, "writer", meter)`), structured output (`OverviewOutput`, `ArticleOutput`). The system prompt is `_contract.md` + `write.md` (`writerInstructions()`); the first user part (cached) is the Expedition's title and summary, every Concept as `id \| title \| Kind`, and the Sources (whole, or with `whole: false` only the segments the batch and its neighbours cite); the second is the batch (each Concept's Kind, aliases, summary, Attributes, citations, Relationships with neighbour links, and for articles its overview), with the goals and the understanding note when given. Overviews: `concept.set` `overview` and `overviewProv`, plus `summary` only where the Concept had none. Articles: `section.create` per section, in order (`keysAfter`), each with its own `prov`; never a second article. `writeBatch` asks once more for Concepts the model left out. `WriteResult`: `{ bodies, written, missing, repairs, unlinked }`. |
| Provenance and links | Every ref must resolve: a Source the writer read, and `findSegments(doc, ref.segment)` non-empty. A ref with a wrong Source id whose segment exists in exactly one Source moves there; one whose quote is found in exactly one segment moves to it; otherwise it is dropped (`repairs`). A quote not in its segment is dropped, keeping the ref. If every ref was dropped, the Concept's own resolving refs stand in (`fallback`). `#c/<id>` links to Concepts that don't exist become plain text (`unlinked`). `unresolvedProv(bodies, sources)` is the guard the jobs run before committing. |
| `writerLabel(state, mode, ids)` | The Change label: "Wrote overviews for Alder C5, Hub motor and 8 more", "Wrote the article for Alder C5". |
| `combineSpend(base, after[])` (`spend.ts`) | The meter after steps that ran side by side from the same `base`: the base plus each one's spend. |

**Measured** (`scripts/real-write.ts`; not part of `pnpm test`: `node --env-file=../../apps/worker/.dev.vars --experimental-transform-types scripts/real-write.ts <ebike-chat|research-doc> [--cap 2] [--model id] [--dry]`): on the e-bike build export (`fixtures/builds/ebike-chat.json`, 50 Concepts, 6 core) on Sonnet 5.5, 7 calls in 227 s for $0.41 billed: every Concept has an overview (76–133 words), all 6 core Concepts have articles (250–413 words, 23 sections), 162 provenance refs, all resolving (none needed repair), 201 in-text links (1 to a Concept that doesn't exist, unlinked). The output is `fixtures/builds/ebike-chat.written.json` (Library → Import) and `.written.summary.json`. `--dry` runs `writerScript` instead: no key, no spend, nothing written.

### Grow (spec §5.5, WP-4.4)

`curator/grow.ts`: the curator agent scoped to one ask. Like the build's stages it never writes: every model step's staged ops are cut into reviewable items and handed to `onItems`, which `@seply/server`'s `grow` job writes to the ask's one Proposal, so items stream while the agent works.

| Export | What it is |
|---|---|
| `grow(o)` → `GrowResult` | One ask (`GrowAsk`: the reader's `text`, or a Concept `action` about `conceptId`; `viewId`, the View they're on). The tools are `concept_create` (refused without a `summary` and an `overview`: new Concepts arrive complete), `concept_update`, `relationship_add` and `search_existing`, plus `source_read` when there are Sources and `view_inspect` (the reader's View, with the suggestions in it) when `views` and `viewId` are given; no View building, no Attributes, no removals, never a commit. An overview linking `#c/<id>` to a Concept that doesn't exist is refused (`badLinks`), since an item can't be fixed once it streamed. After each step the new ops go to `onItems(items, state)`; also when the loop ends early (Stop through `abortSignal`, `SpendingCapReached`, an error), so what came out is kept; then it rethrows. `earlier` (a resumed ask's item count, already in `state`) tells the agent not to repeat them. The prompt: `_contract.md` + `grow.md` (`growInstructions()`), the Sources (or a note that there are none: background knowledge), then the lean Concept index (`conceptIndex`: `id \| title \| Kind \| Tags \| aliases`, and the Relationships; summaries come from `search_existing`), the Concept an action is about with its summary, overview and Relationships both ways, the View, and the ask. `GROW_MAX_STEPS` (24). |
| `itemsFrom(bodies)` | One step's ops as items: a `concept.create` with its own later edits; each Relationship alone; each existing Concept's edits together. |
| `growRationale(ask, state)` | The Proposal's rationale: the reader's words, or "Add what's missing to understand QLoRA", "Add examples of QLoRA", "Suggest Concepts related to QLoRA". `GROW_ACTIONS`, `GROW_ACTION_LABELS` (the panel's words). |
| `estimateAsk({ provider, models, sourceChars, concepts, relationships })` (`estimate.ts`) | One ask on the curator model: the playbook, Sources and Concept index cached, `ASK_STEP.steps` (6) steps of `outputPerStep` (1,500). Shown before asking, next to the per-ask cap. `growSize(state)` counts the Concepts and Relationships. |

**Measured** (`apps/server-node/scripts/real-grow.ts`, the instance key through the AI Gateway; not part of `pnpm test`): "What would I need to understand QLoRA?" on the compute sample (201 Concepts, 425 Relationships, no Source text) on Opus 5.5: 4 calls in 47 s, **$0.35 billed** (the meter agreed; `estimateAsk` says $0.35, with more output and less cache writing than it measured), 12 items streamed in two batches (4 new Concepts, each with a summary and an overview, and 8 Relationships, 3 of them linking Concepts that were already there), all applying when accepted. The Proposal and a summary are in `fixtures/grow/` for owner review. A first run before the lean index and the link check cost $0.43 and left two overview fixes as extra items; both were changed for that.

### MCP tools (spec §6, WP-5.4)

`mcp.ts`: the MCP tools' definitions, shared with the curator's tools so MCP and in-app AI can't drift. Nothing here touches a database or a transport (the server serves them; phase 2 can serve them on loopback).

| Export | What it is |
|---|---|

| `MCP_SCOPES`, `McpScope`, `MCP_SCOPE_LABELS` | `expeditions:read`, `expeditions:create`, `proposals:write`, and their words for the consent screen and Settings. |
| `MCP_INSTRUCTIONS` | The server's instructions: the `seply-learn` skill's SKILL.md without its front matter (`SKILL_TEXT` in `playbook/generated.ts`). |
| `ProposeItem`, `ProposeChangesInput`, `stageProposal({ state, items, views?, sources?, newId? })` | Each item is one curator tool call (`concept_create`, `concept_update`, `relationship_add`, `relationship_remove`, `view_build`) with its input as that tool takes it; `ref: "new:…"` names what an item creates, and later items use it (as an id, a record key or an overview link `#c/new:…`). Items run one at a time over the Expedition with the earlier ones applied; a refused item is skipped with its reason. A View is taken only when `view.inspect` passes, and goes in ready. Returns per-item results, one Proposal item per taken item, and the temp ids' real ids. |
