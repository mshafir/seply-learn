The evidence behind the design is the seeding prototype, [`prototypes/seeding/`](../../../prototypes/seeding/README.md): a staged pipeline found the right Concepts but lacked judgement in its Views, and a **curator agent** with the whole Source in context matched hand-made quality in review.

## 5.1 Engine

- **Core AI SDK 7** (`ai` 7.x): `ToolLoopAgent`, `generateText`/`streamText` with `Output.object`/`Output.array`, and UI message streams with `data-*` parts (`data-viewStatus`, `data-proposal`) keyed by id.
- **Providers:** created per request (Anthropic, OpenAI, Google, or any OpenAI-compatible endpoint) with the instance key or the reader's key. AI Gateway is opt-in only for the hosted instance.
- **No harnesses in v1.** Keep a `HarnessAgent`-shaped seam for a phase-2 "agent mode" on desktop and self-host.
- **Models,** with tested defaults per provider that can be overridden in Settings (per stage under Advanced):
  - a **fast** model for the skim;
  - a **strong** model for the curator agent (the structure is where judgement pays);
  - a **mid-tier** model for the writers.

## 5.2 Building an Expedition

1. **Segment the Sources** (no LLM).
   - The raw file is kept as a blob, alongside normalized markdown split into **segments**: chat turns (speaker and index), PDF pages, document headings and paragraphs.
   - Provenance refs point at segments.
   - Chat exports and pasted chats are parsed, with speaker detection for pasted text.
2. **Skim** (fast model, ~10–20 s):
   - It reads a sample: the first and last segments, every user turn, and the headings.
   - It proposes 4–8 Views, each with an id, View Type, question and why, ranked. The first is the proposed best View.
   - It names the Expedition.
   - Its catalog is each View Type's `answers`, "Draws on" and "Building it from a source".
3. **The curator agent** (strong model; `ToolLoopAgent`) starts at the same moment and runs as a `JobRunner` job:
   1. It reads the whole Source set when it fits in context. Otherwise it falls back to segmenting into chunks and merging, matching on normalized titles and aliases.
   2. It writes an **understanding note**: what the reader wanted, what they decided, what's still open. The note stays in the job and isn't shown.
   3. It builds the **Concept set** and commits it as one Change ("Found 84 Concepts in 3 Sources"). The live counter on Choose Views ticks up as it goes.
   4. It builds **each chosen View** through tools, runs **`view.inspect` checks and self-review** against the View's question, and **commits each View as its own Change**. That streams the View in, and each commit is a checkpoint. A View the Sources can't support **fails with a plain reason**.
4. **Writers** (mid-tier model, in parallel batches of about 10) run after the structure. They write a summary and an **overview** for every Concept, then **articles for core Concepts** in ordered sections with provenance per section. Other Concepts get "Write the article", which editors trigger.
5. **Later additions:**
   - **"Suggest more Views" / "Ask for a specific View"** re-run the skim or the View stage. The new View, and any new Concepts it needs, are created directly. Changes it would make to existing Concepts become a Proposal.
   - **A Source added later** is segmented and read by the agent, and what it adds becomes **one Proposal**.

## 5.3 Tools and checks

The agent writes only through **tools**. Each call is validated against the `packages/domain` Zod schemas, and none takes free-form JSON.

- **Tools:**
  - `concept.create/update`
  - `relationship.add/remove`
  - `attribute.define`
  - `view.build` (settings and overrides)
  - `view.inspect`
  - `source.read(segments)`
  - `search_existing(title|alias)`
- **`view.inspect`** returns what a reader would see (the table cells with priorities, the outcome with its causes and levers, the outline tree, the path to a target) and the **checks**. Both come from the prototype's `validate.py` and the layout metrics:
  - dangling ids; Concepts with more than one `part-of` parent
  - table columns at least ~70% filled **after filling**, with class-level statements ("enclosed printers run ABS") applied to every member
  - a `priority` on every criterion column
  - `chosen` only with a **cited reader decision**, never assistant advice
  - Cause & Effect: the outcome is the reader's concern, in their words; no lever→lever links; build steps folded explicitly
  - **layout metrics** (see [Views §4.4](04-views.md#44-layout-quality-as-a-check))

  A View with problems can't be committed.
- **Where it runs:** the tools and checks live in `packages/ai`; the reader rendering and layout metrics live with the renderers in `packages/views` (`@seply/views/inspect`). `ai` reads them through a `ViewReader` port, and Source segments through a `SourceReader` port, which the app running the job fills ([Architecture §2.1](02-architecture.md#21-monorepo)).
- **The agent may reshape structure** (targets, pins, `placement`, real links) to fix layout. It **never sets positions**, and never pins Weight on a guess about one reader.

## 5.4 The playbook

- **The agent's instructions** are the seeding prompts, moved to `packages/ai/playbook/`:
  - `_contract.md`: shapes, the built-in Kinds and Relationship Types, provenance, and the Weight rule
  - `skim.md`, `extract.md`, `merge.md`, `build-view.md`, `write.md`
- **They carry every rule learned in review:**
  - topic hubs named in the reader's words, and one `part-of` parent each
  - `question` and `goal` Kinds
  - short takeaway titles; quantities as Concepts
  - density targets, and group Concepts for options the Sources treat together
  - "fill before you filter"; one row per real choice
  - the reader's own situation as a person Concept
- **Shared with MCP:** the same files are the `seply-learn` skill's guidance for MCP agents ([MCP §6](06-mcp.md)).

## 5.5 Grow (in-app AI)

- **Owners and editors only.**
- **The same curator agent and tools,** scoped to one ask. The difference is that every write lands in **one Proposal per ask**, streamed as `data-proposal` parts so items appear dashed as they arrive.
- **Asks come from:**
  - the "Ask about this Expedition" box;
  - **Concept actions:** "Add what's missing to understand this", "Add examples", "Write the article", "Suggest related".
- **New Concepts** arrive with a summary and overview.
- **The ask becomes the Proposal's rationale.** The chat transcript isn't stored.
- **Stop** keeps what already streamed, and a **per-ask spending cap** applies (default $0.50).

## 5.6 Keys, cost and limits

- **Key mode** is per instance: an **instance key**, or **bring your own key** (encrypted server-side; see [Architecture §2.6](02-architecture.md#26-auth-keys-and-tokens)). Viewing and editing never need a key.
- **Builds:**
  - An **estimate** is shown before Create. It covers the agent's reads (with prompt caching), its tool loop and the writers.
  - **Spending cap:** 2× the estimate by default. Reaching it **pauses** the job with Continue or Stop.
  - **Cancel** keeps the committed Views.
  - Each step **retries automatically twice** (rate limits, timeouts). Then the View fails, and **Retry** reruns only that View.
- **Size caps:** 25 MB per file, plus a per-Expedition token cap shown up front. Over the cap, the reader picks Sources or sections.
- **Phase 2:** usage caps and quotas on a shared instance key.
