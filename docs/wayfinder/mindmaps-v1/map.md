## Destination

A **build-ready v1 spec plus an implementation game plan** for **Umbel Learn** (formerly Mindmaps), the collaborative, LLM-assisted tool for exploring Expeditions. The spec fixes the domain model, architecture, deployment topology, screens and v1 scope, and sketches phase 2. The game plan cuts the build into milestones and agent-sized work packages with acceptance checks and parallel lanes. Nothing is left to decide before agents start building. Static **sample graphs** and the **app-flow design canvas** light the way.

## Notes

- **Product:** **Umbel Learn** (placeholder name and branding; Umbel is the umbrella for separate LLM tools: Learn, Work, Plan).
- **Vocabulary:** [`CONTEXT.md`](../../../CONTEXT.md) is the glossary (Expedition, Source, Concept, Concept Kind, Attribute, Weight, Tag, Relationship, Relationship Type, View, View Type, Reading status, Visibility, Collaborator, Change, Fork, Proposal). **Graph was renamed Expedition** on 2026-09-25; older tickets and the prototypes still say Graph, so read it as Expedition.
- **View Types:** standardized definitions live in [`docs/view-types/`](../../view-types/README.md), one file per type, following `_template.md`. Use its terms; update it as terms change (domain-modeling skill).
- **Skills for every session:** grilling + domain-modeling for decisions. Record ADRs in `docs/adr/` only for hard-to-reverse, surprising trade-offs.
- **Execution override:** building is allowed **only** for the static sample-graph sites and the chat/doc → graph seeding workflow (prototype tickets). Everything in the real product stays planning-only.
- **Tech givens (fixed by the user):** React Flow + Tailwind/shadcn **with Base UI** as the primitive library, prebuilt components wherever possible and every divergence flagged explicitly; **dark mode** required; the **newest AI SDK** for in-app AI: **core AI SDK 7 in v1** (confirmed 2026-09-25), with pluggable harnesses as a later, optional "agent mode" on desktop/self-host; pnpm + Turborepo TypeScript monorepo; mise for tool installs; Electron desktop app plus a self-hostable SPA with a separate backend persisting to Postgres; easy self-hosting, with the user's own instance on Cloudflare; Better Auth with Google social login by default; Vercel AI SDK for bring-your-own-key LLM features; an MCP server plus skills for agent access.
- **Decided while charting:**
  - Destination is a v1 spec with phase 2 sketched. Views are **in v1 scope** as a flexible, built-in primitive.
  - Relationship Types and Concept Kinds start from a built-in default set that each Graph can extend.
  - People in the subject are Concepts of kind *person*, so the people View is just another set of Relationship Types.
  - Concepts are local to one Graph (cross-graph linking is later).
  - Weight is computed from structure and can be overridden by a curator.
  - LLM changes (in-app or MCP) land as Proposals for a human to accept or reject.
  - v1 collaboration: shared editing with editor/viewer roles, recorded as operations. Real-time co-editing is phase 2, but the v1 data model must not block it.
  - Visibility: private / unlisted / public, and viewing doesn't need login.
  - ~~Snapshots~~: dropped by the Core data model decision; history is Changes from the op log, plus Fork.
  - ~~Electron is local-first with optional sync~~: moved to phase 2 by the Deployment topology decision (v1 is a PWA with read-only offline).
  - Search covers every Graph the user can see (theirs, shared, public), by free text and Tags. Semantic search is phase 2.
  - Seed sources for the sample graphs: pasted or shared chat text, and research docs (e.g. `docs/research/knowledge-graph-learning-tools.md`).
- **Implementation direction (decided 2026-09-25):** first milestone is the **web app on Cloudflare**; every screen on the canvas is v1, phased read → create → grow → share; self-host and desktop follow. Builders are **Claude agents in parallel lanes**, so the game plan cuts work into agent-session-sized packages with acceptance checks.
- **Real-time in v1:** presence and live cursors are on the canvas, so the Expedition's live relay (Durable Object on CF, a Node equivalent when self-hosted) is v1, not phase 2. The op log stays the source of truth; see Client sync layer and live relay.
- **Settled from the fog (2026-09-28):**
  - *Weight and the default View:* Weight is computed from structure, with curator pins. Each Expedition opens on a curator-chosen best View (default: the first to finish building).
  - *Corrections:* the built-in `corrects` Relationship Type links the correction to what it corrects.
  - *Built-in default set:* the Kinds and Relationship Types listed in the seeding contract ([`prototypes/seeding/prompts/_contract.md`](../../../prototypes/seeding/prompts/_contract.md)).
  - *Concept time (v1):* a point or span, precision taken from the string, an approximate flag, a lane. BCE, eras and "circa" are phase 2.
  - *Snapshot compare / restore:* dissolved into Changes.
- **Tracker:** local markdown. See [`docs/wayfinder/README.md`](../README.md).

## Decisions so far

<!-- one line per closed ticket: [title](tickets/NN-slug.md): gist -->

- [Backend runtime for Cloudflare and self-hosting](tickets/04-backend-runtime-cloudflare-and-selfhost.md): one Hono app with two entrypoints: a CF Worker (SPA assets, Hyperdrive → `pg` → Drizzle) and a Node/Bun container with docker-compose Postgres. Shared Better Auth, MCP streamable HTTP, and AI SDK streaming. Real-time path: Durable Object per Graph on CF, Hocuspocus when self-hosted *(self-host part superseded by Client sync layer and live relay: in-process rooms + Postgres LISTEN/NOTIFY)*.
- [React Flow layouts for Views](tickets/06-react-flow-pivot-layouts.md): each View is its own function that computes positions, and React Flow 12 just draws them. Layouts: elkjs (dagre fallback) for prerequisites, custom d3-scale timeline, d3-hierarchy radial for people, d3-force for weighted. View switches animate by Concept id with d3-timer (no React Flow Pro needed).
- [Local-first sync for Electron and Postgres](tickets/05-local-first-sync-engine.md): hand-roll a per-Graph op log (Electron SQLite plus a pending-ops queue; the server appends to Postgres in per-Graph order; push/pull with role checks). Snapshot = a named point in the log; Proposal = a pending op batch; restore adds new ops. Loro/Yjs only for phase-2 rich text. Electric, Zero, and PowerSync rejected (sidecar servers, weak offline writes, licensing). LiveStore is the runner-up to watch.
- [Sample graph file format and static viewer](tickets/01-sample-graph-format-and-viewer.md): static viewer with three graphs from real chats. The format (`types.ts`) is the candidate export. Concepts have built-in default **Kinds** (extendable), typed per-Graph **Attributes**, a date and/or conversation order, and geo. Relationships carry notes.
- [View prototypes on the sample graphs](tickets/03-pivot-prototypes.md): "Pivot" is renamed **View**. A **View Type** is a set of instructions for a way of looking at knowledge, not a strict filter plus Relationship Types. Six are documented in [`docs/view-types/`](../../view-types/README.md): Comparison Table, Outline, Evidence, Cause & Effect, Map (real basemap), Timeline (purpose-built component). "Packs" means View Types; the Kinds/Relationship-Types bundle idea is dropped. The prototype now renders only these six, with vis-timeline for Timeline and MapLibre + OpenFreeMap for Map; the rest are written up as [candidates](../../view-types/README.md#candidates-needing-more-passes). A third pass on a learning chat added experimental View Types (Anatomy, Learning path, Lineage, Quadrant, Rates & estimates; Maturity ladder folded into Quadrant, Misconceptions set aside). A fourth pass gave Concepts an overview and an optional article, read in the side panel.
- [Remote MCP server, auth, and skills](tickets/07-remote-mcp-and-skills.md): one stateless streamable-HTTP `/mcp` route in the backend (MCP TS SDK v2, spec 2026-07-28; runs on CF and Node). Better Auth ≥1.7 is the OAuth authorization server (`@better-auth/mcp` + CIMD), with personal API tokens as a fallback. Coarse scopes, with Graph access checked against the Collaborator role on every call. MCP writes only Proposals. Skills ship as an Agent Skills plugin and are mirrored in the server instructions. No local stdio server in v1.

- [App layout and page flow](tickets/12-app-layout-and-page-flow.md): designed on a Claude Design canvas ([record](prototypes/app-flow.md)). Expedition screen = Views rail · canvas · side panel, with View settings behind a floating View button. Expeditions start from any mix of Sources, and the only review step is choosing Views. Building never blocks: Views stream in one at a time. Reading status is per reader. AI and MCP edits are dashed Proposals, and public links point at frozen Snapshots. Graph renamed Expedition; product named Umbel Learn.
- [AI SDK and pluggable harnesses](tickets/13-ai-sdk-harness-research.md): the harness layer is real (AI SDK 7, `@ai-sdk/harness`, experimental) but plugs in sandboxed coding agents (Claude Code, Codex, Pi, ACP) with no Cloudflare sandbox. So the build pipeline and Grow use core AI SDK 7 (`streamText`/`ToolLoopAgent` + `Output.object`, `data-*` parts per View; CF Workflows + the Expedition's Durable Object). BYOK means a per-request provider with the reader's key; AI Gateway only as opt-in. Harnesses become an optional "agent mode" on desktop/self-host, not v1 on Cloudflare. [Findings](research/ai-sdk-harness.md).
- [shadcn with Base UI, component inventory and dark mode](tickets/14-shadcn-base-ui-inventory.md): Base UI is shadcn's default since 2026-07 (`@base-ui/react` 1.8, CLI 4.21; no Sonner, use its Toast). `shadcn init -t vite --monorepo` gives `apps/web` + `packages/ui` on Tailwind v4; Electron is another workspace. 98 canvas UI elements: 86 prebuilt/composed, **8 divergences** (Expedition canvas, View renderers, Thumbnails, live cursors, step indicator, drop zone, Attribute list, extra Badge variants). Dark mode: `.dark` tokens + React Flow `colorMode`, OpenFreeMap positron/dark or Protomaps flavours, a hand-written vis-timeline dark sheet, Typeset prose; Electron via `nativeTheme.themeSource`. [Findings](research/shadcn-base-ui.md).
- [Core data model and operation log](tickets/08-core-data-model-and-operations.md): one per-Expedition log of field-level ops (client ULIDs, last-writer-wins per field, tombstones with cascade) covers everything shared; Collaborators, Visibility and per-reader state sit outside it. **No Snapshots:** history is a list of **Changes** (undo per Change skips later edits, view-as-of, restore appends ops), public links show the latest state, and **Fork** makes a separate copy ([ADR](../../adr/0001-history-from-the-op-log-no-snapshots.md)). A Proposal is a pending op batch whose items are flagged "changed since proposed". Articles are ordered sections with their own provenance; Relationships are unique per (from, type, to); built-ins are referenced by id; layouts are always computed; a View's build status is in the log and its progress is live-only. Sources are entities with blobs, visible to any viewer. Roles are owner/editor/viewer, and "can suggest" isn't a role. **Schema:** relational tables + JSON columns, one Drizzle schema (Postgres-only in v1, see Deployment topology); Zod settings schema per View Type; Merge with aliases; fractional order keys; fixed per-type thumbnails; Learn-only accounts for v1; 30-day Trash.
- [Client sync layer and live relay](tickets/20-client-sync-layer-and-live-relay.md): our own op engine (confirmed ops, pending queue, rebase, undo, view-as-of, Proposal preview; SQLite in Electron main, in-memory on web) with **TanStack DB** (0.9, MIT) on top as the live-query layer via custom sync; its persistence and offline outbox are not used. TinyBase and Replicache rejected. v1 live relay = one WebSocket room per Expedition (hibernating Durable Object on CF; in-process rooms + Postgres LISTEN/NOTIFY self-hosted, no Hocuspocus): pushes stay HTTP, and the room fans out ops, presence, cursors and build progress. Phase-2 text leans Yjs; the v1 schema doesn't change. First build step: prototype TanStack DB optimistic updates over the op engine. [Findings](research/client-sync-layer-and-live-relay.md).
- [Deployment topology and monorepo layout](tickets/09-deployment-topology-and-monorepo.md): split by layer, with 3 apps (web, worker, server-node) and 7 packages (domain, sync, server, ai, views, ui, config). CF = one Worker + Expedition DO + Workflows behind our own JobRunner, **Neon** via Hyperdrive, and R2. Self-host = one Node container (pg-boss) + Postgres, with blobs on a volume or S3. **No Electron in v1**: an installable PWA with read-only offline (last ~10 + pinned). No offline edits, and the schema is Postgres-only. GitHub Actions with a preview Worker + Neon branch per PR.
- [Per-reader state](tickets/16-per-reader-state.md): three per-user tables (reading status, personal View settings, reading position) outside the op log, last write wins. Private in v1. Anonymous readers keep state in the browser and it is adopted on sign-in. Merge keeps the higher status. Every View checks read Concepts, and only Learning path and Outline skip or hide them. Personal settings default from the View Type only. Continue reading resumes the last spot per Expedition.
- [Sources and the build pipeline](tickets/15-sources-and-build-pipeline.md): v1 takes pasted text and files (no link fetching). Sources are kept raw plus segmented text; provenance = {source, segment, quote}. A fast skim proposes Views while extraction runs behind. Extraction and each View commit as their own Changes (the preview streams live). Overviews for all Concepts, articles for core Concepts only. Large inputs are chunked and merged, with a 25 MB/file cap and a token cap. Keys: the operator either provides an instance key for everyone or requires each reader's own (stored server-side, encrypted); caps on a shared key are v2, with per-stage default models, an estimate, a spending cap and per-View retry. Notification is in-app + web push. Later Views are direct and their edits to existing Concepts are proposed; a later Source becomes a Proposal. **Amended 2026-09-28:** the builder is a **curator agent** (`ToolLoopAgent`) working through validated tools. Checks, including layout metrics from the real layout code, block a View's commit; the agent reshapes structure but never sets positions. The seeding prompts become its playbook. The skim, per-View commits and retries, keys and caps are unchanged; chunking is only a fallback.
- [MCP tool surface and skills](tickets/10-mcp-tool-surface-and-skills.md): layered read tools (list/get Expedition, get_view in its own shape, get_concept with depth and neighbours, search, Source segments) as compact markdown. `create_expedition` writes an agent-extracted first build directly. `propose_changes` is one batch Proposal (+ list/withdraw). MCP never spends an API key. No reading state, history, Fork or sharing in v1. Scopes: expeditions:read/create, proposals:write. One `umbel-learn` skill that shares its prompts with the build pipeline.
- [Design system, theming and dark mode](tickets/17-design-system-and-dark-mode.md): warm charcoal dark palette, contrast-checked, with a darker amber for light-mode text. 12 named Kind colours stored by name. Plex Sans/Mono + Newsreader self-hosted via Fontsource; shadcn Typeset for prose. System/Light/Dark toggle in the account menu, set before first paint; resolvedTheme drives React Flow, MapLibre (positron ↔ dark) and a vis-timeline override sheet. All 8 divergences accepted and listed in `packages/ui/DIVERGENCES.md`. Placeholder wordmark + umbel glyph.
- [Seeding workflow from chats and docs](tickets/02-seeding-workflow.md): a staged pipeline found the right Concepts (96–100% judged recall vs hand-made) but its Views lacked judgement. A **curator agent** with the whole Source, the prompts as a playbook, validated tools and self-review matched the hand-made quality in the user's review. Deliverables: the playbook prompts, `validate.py` + layout metrics, segmentation. Found along the way: Views competing for shared `part-of` (for the spec); risk-mode Cause & Effect as a ranked list around a central outcome; Learning paths laid out on the visible subgraph by topic.
- [In-app AI expansion and Proposal review](tickets/11-in-app-ai-expansion-and-proposal-review.md): owners and editors only. Grow reuses the curator agent and tools, with one Proposal per ask streamed dashed onto the canvas. Asks come from the side panel box or Concept actions (missing prerequisites, examples, article, related). New Concepts arrive with summary + overview. The Suggestions tab reviews per item (dependencies included, each action one undoable Change, stale flagged). The ask is kept as rationale; the chat is not. BYOK keys are AES-GCM encrypted server-side and never returned. Per-ask cap and Stop. UI says "Suggestions", the domain says Proposal.
- [View-specific structure](tickets/24-view-specific-structure.md): shared `part-of` is the default structure. Each View can override placement, sibling order, hide and explicit folds in its settings. Re-parenting asks "just this View" or "everywhere". Overrides follow Merge and pause while a Concept is deleted. Settings are edited by path-level ops, and `outline_key` is dropped.
- [Permissions table](tickets/23-permissions-table.md): editors do everything content-related, including AI, accepting Proposals, undo and restore, and inviting editors or viewers. Only the owner changes roles, removes people, changes Visibility, transfers ownership or deletes. Viewers read and Fork. Tokens and MCP inherit the user's role and write only Proposals.
- [Search](tickets/22-search.md): Postgres full-text (weighted tsvector + GIN, pg_trgm for fuzzy titles). Global search covers mine + shared, with a public opt-in, grouped by Expedition / Concept / Tag, with access enforced in the query. Search inside an Expedition runs client-side and works offline. Semantic search is phase 2.
- [Map basemap for hosted and self-hosted](tickets/21-map-basemap-for-hosted-and-self-hosted.md): our own Protomaps PMTiles copy (R2 when hosted, volume/S3 when self-hosted), light ↔ dark flavours, no keys. OpenFreeMap as a configurable fallback. A bundled coarse world layer covers offline and failures; tiles already viewed are cached. The extract size is to be checked in the build.
- [Import and export](tickets/25-import-and-export.md): any viewer can export canonical versioned JSON (current state, optional Source files) plus an Obsidian-readable Markdown folder. No history, Proposals or reader state. Import takes our own JSON only, as a new private Expedition via a first build with ids re-minted. Markdown import is phase 2.

- [Invites and email](tickets/26-invites-and-email.md): invites send transactional email (hosted provider, optional SMTP when self-hosted), plus an invite link and in-app inbox. Build notifications stay in-app + web push.
- [Assemble the v1 spec](tickets/18-assemble-v1-spec.md): written at [`docs/spec/v1/`](../../spec/v1/README.md) (8 sections, each linking its tickets). Six assumptions are listed for review; one gap (invites) went back on the map and was decided.
- [Implementation game plan](tickets/19-implementation-game-plan.md): written at [`docs/plan/v1/`](../../plan/v1/README.md): 39 work packages across M0 (foundations and spikes) → M1 skeleton on CF → M2 read → M3 create → M4 grow and collaborate → M5 share + MCP → M6 self-host. Tracked as GitHub Issues/PRs with previews; 3–4 agent lanes; the owner reviews milestones and data/auth/AI PRs; unit + e2e testing only (accepted risk). **The map has reached its destination.**
