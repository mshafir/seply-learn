# web

**Lane:** D: App & UI

## Contract

The Vite SPA (installable PWA): routes and screens from docs/spec/v1/03-screens-and-flows.md, composed from @seply/ui, @seply/views and @seply/sync.

### Routes (wouter)

| Path | Screen |
|---|---|
| `/sign-in?next=<path>` | Sign in: "Continue with Google" starts Better Auth's Google flow (`POST /api/auth/sign-in/social`) and comes back to `next` (a same-site path; default `/`). |
| `/` | The Library (spec §3.2, WP-2.7; `src/screens/library.tsx`, pure parts in `library-sections.ts`, unit tested): **Continue reading** (my 3 most recently read Expeditions, `GET /api/reader/recent`, with their thumbnails; hidden when empty), then **Your Expeditions** (mine, built or building), **Shared with you** (others', as editor or viewer) and **Drafts** (not built yet, that I can edit), from `GET /api/expeditions`. A side nav counts the sections and holds the **Tag filter** (a ToggleGroup of the Expedition Tags in the list, with counts; one at a time, click again to clear). **Cards**: the fixed thumbnail of the best View's View Type (`@seply/ui` `ViewTypeThumbnail`, never a preview of the Expedition), title, summary, the collaborators' avatars with a short summary ("Only you", "You and Ada"), Concept and View counts, status (Draft, Building), my role when not the owner, the date it last changed, and a **pin** (Toggle, "Keep available offline"). Offline, the Library says so and lists the Expeditions saved on this device. **New** creates an untitled draft (`POST /api/expeditions`) and opens it in the create flow (`/new/:id`; a Drafts card I can edit opens there too); **Import** posts a JSON file to `/api/import` and opens the result. **Global search** ("Search Concepts, articles and #tags", or ⌘K/Ctrl+K; `src/components/global-search.tsx`) opens a shadcn Command dialog over `GET /api/search`: results grouped by Expedition, Concept (with its Expedition) and Tag, an "Include public Expeditions" switch, `#tag` filters, and picking a Tag puts it in the query. A Concept opens as `/e/:id?concept=<conceptId>`, with its side panel open. |
| `/e/:id` and `/e/:id/:viewId` | The Expedition screen (spec §3.6) on a View: the URL's, else where I left off (Continue reading), else the best View, else the first. |
| `/new/:id` and `/new/:id/views` | The create flow (spec §3.3, §3.4, WP-3.4; `src/create/`, pure parts in `flow.ts`, unit tested), for a draft I can edit (signed in; a built Expedition, or a viewer, goes to `/e/:id`). A header with "Library", the **step indicator** (Sources → Choose Views → Open) and the account menu. **Sources** (`sources-step.tsx`): Tabs for "An AI chat" (paste; `POST /api/sources/:id` `{ type: "paste" }`), "Files" (the drop zone, several at once; multipart) and "Just a prompt"; the goal chips ("learn it", "decide", "plan": a ToggleGroup); the Sources list ("Pasted chat · 6 turns", "PDF · 3 pages") with Remove (`DELETE /api/sources/:id/:source`); the estimate ("Estimated cost to build: ~420k tokens, about $1.10", `POST /api/ai/estimate` with the Sources' characters, with where the build stops), or what's missing (no key: a link to Settings); over the token cap, a warning and Next disabled until Sources are removed. **Choose Views** (`choose-views-step.tsx`): the skim (`POST /api/expeditions/:id/skim`) with a progress bar while it reads; its Views as cards (the View Type thumbnail and name, the question, why; a Checkbox; "Opens here" on the first chosen), the 3–4 best chosen; the title (the skim's, unless the draft has its own); "N Concepts found across M Sources" (the draft, polled every 3 s); "Suggest more Views" and "Ask for a specific View" (the skim again, never repeating a card). **Save draft** saves the title and the chosen Views, queued, best first (`PUT /api/expeditions/:id/plan`) and goes to the Library; **Create Expedition with N Views** saves the same, then calls `startBuild` (`POST /api/expeditions/:id/build`, the hand-off to WP-3.5b; until then it answers 501 and the reader is told the draft is saved). The skim's cards are kept for the tab in `sessionStorage` (`seply-create:<id>`, keyed by the Sources' ids), so a reload doesn't skim again; a reopened draft shows its saved Views. |
| `/settings` | Settings (spec §3.10, WP-3.3; `src/screens/settings.tsx`), opened from the account menu. The **AI** card over `GET /api/ai`: in bring-your-own-key mode, a row per provider (Anthropic, OpenAI, Google, Vercel AI Gateway): a password field and Save, or, once stored, the key's last 4 characters with Test (the server checks it with the provider; a toast says whether it works) and Delete; "Builds use" (a Select, with keys for more than one provider); **Advanced**: the model per stage (skim, curator, writers) on that provider, defaults as placeholders. In instance mode it says the instance's key pays. In both, the **spending cap per ask** ($, default $0.50, at most $50). A key goes up once, when saved, and never comes back. Theme stays in the account menu; Connected agents and Notifications come with their work packages. |
| `/showcase` | Every token, Kind hue, type style and component, in both palettes (WP-0.3). |

`/` needs a session (`GET /api/me`); signed out, it redirects to `/sign-in`. `/e/*` opens signed out too: a public or unlisted Expedition reads without a login (read-only, with "Sign in" in the header); a private one is "not found", with a Sign in button. The last signed-in user is kept in `localStorage` (`seply-user`) so a reload without a connection can still load that user's pending edits.

### The Expedition screen

- **Header** (`h-14`): the glyph back to the Library, the title (owners and editors rename it in place, through the sync client), **search inside the Expedition** ("Search text or #tag", `src/expedition/concept-search.tsx`: client-side over the loaded Concepts' titles, aliases, summaries and Tags, so it works offline; every word must match, `#tag` by Tag prefix; the canvas dims the rest through `ExpeditionView`'s `matches`, a badge counts matches, Escape clears; `matchConcepts` in `src/lib/search.ts`, unit tested), sync status ("Saving", "Offline · N edits waiting") and the **account menu** (name, theme System / Light / Dark, sign out).
- **Views rail**: shadcn `Sidebar` at `--sidebar-width: 272px`, under the header; each entry is the View's name and question. Below 768 px it is a Sheet opened from the header.
- **Canvas pane**: as wide as possible. `src/expedition/canvas-slot.tsx` mounts `@seply/views`' `ExpeditionView` on the sync client's collections with the selected View and Concept. The **View button** (icon, name, question, settings icon) floats over its top-left corner and opens the View panel; the View is drawn below it.
- **Side panel**: 440 px (`w-110`), opened by selecting a Concept (the Concept panel) or by the View button (the View panel). Below 1200 px it is a right-hand Sheet.
- **View panel** (spec §3.6, §4.2, WP-2.4): `src/expedition/view-panel.tsx`. The description (the View Type doc's opening paragraph), **shared settings** (owners and editors only), **your settings**, "Duplicate" (editors: a copy of the View next to it, as new ops) and "Read the View Type" (the `docs/view-types/<id>.md` file, bundled at build time by `src/expedition/view-type-docs.ts`). Both forms are generated from the View Type's Zod schemas in `@seply/domain` (`src/expedition/settings/`): `fields.ts` walks a schema into fields (unit tested), `settings-form.tsx` draws them with shadcn Field, Switch, Select, Checkbox, Input and Textarea. The per-View structure overrides (`placement`, `order`, `hide`, `fold`) are not in the form. A shared change is checked against the schema, then written to the View row; the sync client turns it into `view.set` ops by settings path.
- **Personal View settings**: `src/lib/personal-view-settings.ts`. Per reader and View, never shared, defaults from the View Type's personal schema. Read and written through the `PersonalViewSettingsStore` interface; the screen passes the reader's store (`ReaderPersonalViewSettings` in `src/lib/reader.ts`), so they are saved in `personal_view_settings` through the reader API and follow the reader across devices (an anonymous reader's stay in this browser). The localStorage store is the fallback. They reach the View as `personal` (Learning path's "Show all steps" is the same setting as its toolbar toggle; "Hide what I've read" hides covered Concepts).
- **Status chip** (`src/expedition/status-chip.tsx`): View-specific status floating at the bottom of the canvas, e.g. "Path to MLA · 7 of 11 read" (counting the reader's Reading status), with a clear button; the View reports it through `onStatus`.
- **Reading status** (spec §3.7, WP-2.5): under the Concept's title, a ToggleGroup: Not read yet / Read / I knew this. Read and known Concepts get a check in every View (`covered`, passed to `ExpeditionView` with the View's personal settings); the Learning path skips them in its steps, and "Hide what I've read" removes them. Signed out, after the first mark: "Sign in to keep your progress across devices."
- **Reader state** (`src/lib/reader.ts`, `src/components/reader-provider.tsx`): one `@seply/sync` `ReaderClient` per page for whoever is reading (the user, or the browser's anonymous reader), over the IndexedDB reader store. Signed in, marks are saved through `/api/reader` (queued in IndexedDB while offline, saved on reconnect); anonymous marks stay in the browser, and move into the account on sign-in (newest wins). The screen refreshes the reader's state on open and whenever the tab comes back into view (other devices' marks); other tabs hear marks at once.
- **Continue reading**: the screen saves my position (View, the Concept in the panel and its depth) a moment after I stop moving. Opened without a View in the URL, it lands there, with "Continuing where you left off · Back to the start" (the best View, panel closed). Pure parts in `src/expedition/continue.ts` (unit tested).
- **Concept panel** (spec §3.7, WP-1.7): `src/expedition/concept-panel.tsx`, with the pure parts in `reading.ts` (unit tested, `pnpm --filter web test`). A back stack of places: the overview depth (summary, Tags, aliases, Attributes, the overview, "Read the full article", Relationships both ways: "Links to" with each Relationship Type's label, "Linked from" with its inverse label) and the article depth (sections in order). Markdown renders with react-markdown + remark-gfm inside shadcn Typeset (`src/expedition/prose.tsx`; raw HTML is not rendered). In-text `#c/<id>` links and Relationship links push onto the stack; Back pops it; a canvas click starts a new stack. Every overview and article section has a provenance badge: "From the chat, turn N" (segment ids per the seeding contract: `tN` chat turn, `sN` document section) or "Background knowledge". `p2` is a PDF page, and a split segment (`t3a`) reads as its whole. A badge whose Source the Expedition has is a link: it opens the **Source viewer**.
- **Source viewer** (spec §3.7, WP-3.1): `src/expedition/source-viewer.tsx`, a Dialog over the screen (so closing it returns to the panel as it was), with the pure parts in `source-reading.ts` (unit tested). It loads `GET /api/sources/:expedition/:source` and shows the Source's title, a summary ("Pasted chat · 6 turns", "PDF · 3 pages"), the cited segment ("Cited: Turn 5") and "Download the file"; then the segments: chat turns with who said it ("You", or the assistant by its export: ChatGPT, Claude, Gemini) and "Turn N", conversation titles where an export's conversations change, document sections under their headings, PDF pages. The cited segment (every part of a split one) is highlighted (`--suggested`) and scrolled into view. Long Sources draw a window around it (20 before, 40 after), with "Show earlier" / "Show more". A link opened in a new tab (`?source=<id>&segment=<id>`) opens the viewer on load. Offline, or for a Source without stored text (imported from JSON), it says so.
- **Offline reading** (spec §2.9, WP-2.7): the app is an installable PWA (`vite-plugin-pwa`, `vite.config.ts`): the service worker precaches the app shell (HTML, JS, CSS, the self-hosted fonts' Latin subsets, the brand icons), falls back to `index.html` for client-side routes, and caches no API response. Expeditions for offline reading live in IndexedDB (`src/lib/offline.ts`, `@seply/sync`'s `OfflineCache`, database `seply-offline`): the last 10 opened, plus any pinned in the Library, per user. The screen saves the confirmed state when it opens an Expedition and a moment after each change. Opened when the server can't be reached, an Expedition with a saved copy reads from it **read-only** (no renaming, no shared settings, no Duplicate), with the **"Offline, as of … · read-only" chip** in the header (`src/expedition/offline-chip.tsx`, with Retry); the header still counts edits waiting from before. Reading status and position marks still queue (per ticket 16). The screen keeps retrying, at once when the browser comes back online, and the live client replaces the copy. Without a copy it says it can't reach the server. Signing out clears the user's saved Expeditions.
- **Web push** (spec §2.5, WP-3.2): `src/lib/push.ts` has `enablePush()` (asks permission, subscribes this browser with the server's VAPID key from `/api/web-push/key`, registers it at `/api/web-push/subscriptions`; returns `enabled`, `denied`, `unsupported` or `unavailable` when the server has web push off) and `disablePush()`. Nothing calls them yet: the prompt on the first "Leave it building" is WP-3.7. The service worker imports `sw/push-sw.js` (emitted as `/push-sw.js` by a small plugin in `vite.config.ts`), which shows a job's notification (`{ title, body, url, tag }`) and opens or focuses its Expedition on click.
- **Data**: `useSyncClient(expeditionId, userId)` (`src/lib/sync.ts`) opens `@seply/sync`'s client with the fetch transport and the IndexedDB pending store, retries opening with backoff (1 s doubling to 30 s) when the server can't be reached, pulls every 3 s while the page is visible (other tabs' and people's edits, until the live relay of WP-4.1), and disposes it on unmount. `useExpeditionData(collections)` gives the live rows (`useLiveQuery` per collection) for the rail, header and panel.

## Notes

- **Theme:** `index.html` has an inline script that sets `.dark` and `color-scheme` before first paint, from the `seply-theme` key the `ThemeProvider` writes.
- **Public directory** is `packages/ui/brand`, so the favicon and PWA icons are served from the site root and the brand stays one swappable folder. The web manifest (name, icons, theme colours) is generated from `vite.config.ts`; its two colours are the light `--background` and `--primary` tokens as hex, since a manifest can't read CSS.
- **Styles:** `main.tsx` imports `@seply/ui/globals.css`, then `@xyflow/react/dist/style.css`, then `@seply/views/canvas.css` (that order).
